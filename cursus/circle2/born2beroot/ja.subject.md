## 第III章　AIに関する指示

### 背景（Context）

この課題は、42の研修における基礎的な構成要素を発見する手助けをするために設計されています。

重要な知識とスキルをきちんと身につけるためには、AIツールやサポートの利用について思慮深いアプローチを取ることが不可欠です。

真の基礎的な学習には、挑戦・反復・仲間同士の学び合いを通じた本物の知的努力が必要です。

AIに対する私たちのスタンス（学習ツールとして、42研修の一部として、そして就職市場での期待値として）についてのより完全な概要は、イントラネット上の専用FAQを参照してください。

### 主なメッセージ

- 近道をせずに強固な基礎を築くこと。
- 技術力とパワースキルを本当に伸ばすこと。
- 本物の仲間同士の学び合いを体験し、学び方や新しい問題の解き方を学び始めること。
- 結果よりも学習の過程の方が重要であること。
- AIに関連するリスクについて学び、よくある落とし穴を避けるための効果的な管理手法や対策を身につけること。

### 受講者のルール

- AIに頼る前に、まず自分に課せられた課題に対して自分で考えること。
- AIに直接的な答えを求めないこと。
- 42のAIに対するグローバルな方針について学ぶこと。

### フェーズの成果

この基礎フェーズの中で、以下の成果を得ることになります。

- 適切な技術・コーディングの基礎を身につける。
- このフェーズにおいて、なぜ・どのようにAIが危険になり得るかを知る。

### コメントと例

- もちろん、私たちはAIの存在を知っていますし、AIが君の課題を解いてしまうこともできることも知っています。しかしここに来ている目的は学ぶことであり、AIが学習済みであることを証明することではありません。与えられた問題をAIが解けることを示すためだけに、自分の（そして私たちの）時間を無駄にしないでください。
- 42での学びは「答えを知っていること」ではなく「答えを見つける力を身につけること」です。AIは答えを直接与えてくれますが、それではあなた自身の思考力を育てることができません。そして思考には時間・労力・そして失敗が伴います。成功への道は簡単なようにはできていません。
- 試験中はAIが使えないことを覚えておいてください（インターネットもスマートフォンも使用不可）。学習過程でAIに頼りすぎていたかどうかは、すぐにわかるでしょう。
- 仲間同士の学び合いは、異なる考え方やアプローチに触れる機会を与え、対人スキルや多角的に考える力を向上させます。それは単にボットとチャットするよりもはるかに価値があります。だから遠慮せず、話し、質問し、一緒に学びましょう！
- そう、AIはカリキュラムの一部になります ― 学習ツールとしても、学習対象そのものとしても。自分自身のAIソフトウェアを作る機会さえあります。私たちの段階的（クレッシェンド）アプローチについて詳しく知るために、イントラネットで公開されているドキュメントに目を通してください。

**✓ 良い実践例：**

## 第V章　必須部分

この課題は、特定のルールに従って最初のサーバーをセットアップすることで構成されています。

> ⚠️ **注意：** これはサーバーのセットアップであるため、最小限のサービスのみをインストールします。そのため、グラフィカルインターフェースはここでは不要です。`X.org`、`Wayland`、またはそれに相当するグラフィカルサーバーのインストールは禁止されています。これに違反した場合、評価点は0点になります。

オペレーティングシステムとして、`Debian` の最新安定版（testing/unstable版は不可）、または `Rocky` の最新安定版のいずれかを選択する必要があります。システム管理が初めての場合は `Debian` を強く推奨します。

> ℹ️ **情報：** `Rocky` のセットアップはかなり複雑です。そのため `KDump` を設定する必要はありません。ただし `SELinux` は起動時に動作している必要があり、その設定はこの課題の要件に合わせて調整する必要があります。`Debian` の場合も `AppArmor` が起動時に動作している必要があります。

`LVM` を使用して、暗号化されたパーティションを最低2つ作成する必要があります。以下はパーティショニングの一例です。

```
wil@wil:~$ lsblk
NAME              MAJ:MIN RM  SIZE RO TYPE MOUNTPOINT
sda                 8:0   0    8G  0 disk
├─sda1              8:1   0  487M  0 part  /boot
├─sda2              8:2   0    1K  0 part
└─sda5              8:5   0  7.5G  0 part
  └─sda5_crypt    254:0   0  7.5G  0 crypt
    ├─wil--vg-root 254:1  0  2.8G  0 lvm   /
    ├─wil--vg-swap_1 254:2 0  976M 0 lvm   [SWAP]
    └─wil--vg-home 254:3  0  3.8G  0 lvm   /home
sr0                11:0   1 1024M  0 rom
wil@wil:~$
```

> ℹ️ **情報：** 防衛（ディフェンス）の際には、選んだオペレーティングシステムについていくつか質問されます。例えば、`aptitude` と `apt` の違いや、`SELinux` や `AppArmor` が何であるかを知っておく必要があります。要するに、自分が使っているものを理解しておくこと！

仮想マシン内でポート4242番で `SSH` サービスが動作している必要があります。セキュリティ上の理由から、root権限で `SSH` 接続できないようにする必要があります。

> ℹ️ **情報：** 防衛の際には、新しいアカウントを作成することで `SSH` の使用がテストされます。したがって、`SSH` の仕組みを理解しておく必要があります。

`UFW` ファイアウォール（`Rocky` の場合は `firewalld`）を設定し、仮想マシン内ではポート4242のみを開放する必要があります。

> ℹ️ **情報：** 例で示されているディスクサイズは任意のものです。不要なディスク使用を避けつつ正常に動作するよう、各パーティションの適切なサイズを自分で決定する必要があります。

> ℹ️ **情報：** 仮想マシンを起動した際、ファイアウォールが有効になっている必要があります。`Rocky` の場合は `UFW` の代わりに `firewalld` を使用する必要があります。

- 仮想マシンの `hostname` は、自分のログイン名の末尾に42を付けたものにする必要があります（例：`wil42`）。このホスト名はピアレビューの際に変更することになります。
- 強力なパスワードポリシーを実装する必要があります。
- 厳格なルールに従って `sudo` をインストール・設定する必要があります。
- root ユーザーに加えて、自分のログイン名をユーザー名とするユーザーが存在している必要があります。
- このユーザーは `user42` グループと `sudo` グループに所属している必要があります。

> ℹ️ **情報：** ピアレビューの際には、新しいユーザーを作成し、グループに割り当てる作業を行うことになります。

強力なパスワードポリシーを設定するには、以下の要件を満たす必要があります。

- パスワードは30日ごとに期限切れになる必要があります。
- パスワード変更間の最小日数は2日に設定する必要があります。
- パスワードの有効期限が切れる7日前に、ユーザーに警告メッセージが届く必要があります。
- パスワードは最低10文字以上で、大文字・小文字・数字をそれぞれ1文字以上含む必要があります。また、同じ文字が4回以上連続してはいけません。
- パスワードにはユーザー名を含めてはいけません。
- 以下のルールはrootパスワードには適用されません：パスワードには、直前のパスワードに含まれていなかった文字を最低7文字含める必要があります。
- もちろん、rootパスワードもこのポリシーに従う必要があります。

> ⚠️ **注意：** 設定ファイルの準備が終わったら、root アカウントを含め、仮想マシン上に存在する全アカウントのパスワードを変更する必要があります。

強力な `sudo` グループの設定を行うには、以下の要件を満たす必要があります。

- `sudo` による認証の誤ったパスワード入力は、3回までに制限する必要があります。
- `sudo` 使用時に誤ったパスワードが入力された場合、自分で選んだカスタムメッセージが表示される必要があります。
- `sudo` で実行された各操作は、入力・出力ともにログに記録される必要があります。ログファイルは `/var/log/sudo/` フォルダに保存する必要があります。
- セキュリティ上の理由から、TTYモードを有効にする必要があります。
- セキュリティ上の理由から、`sudo` が使用できるパスも制限する必要があります。
  例：`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin`

最後に、`monitoring.sh` という名前のシンプルなスクリプトを作成する必要があります。`bash` で記述する必要があります。

サーバー起動時、このスクリプトは以下に挙げる情報を全ての端末に表示し、さらに10分ごとにも表示します（`wall` コマンドを参照）。バナーは任意です。エラーは一切表示されてはいけません。

このスクリプトは常に以下の情報を表示できる必要があります。

- オペレーティングシステムのアーキテクチャとそのカーネルバージョン
- 物理プロセッサ数
- 仮想プロセッサ数
- サーバー上で現在利用可能なRAM容量とその使用率（パーセンテージ）
- サーバー上で現在利用可能なストレージ容量とその使用率（パーセンテージ）
- 現在のCPU使用率（パーセンテージ）
- 最後の再起動の日付と時刻
- LVMが有効かどうか
- アクティブな接続数
- サーバーを使用しているユーザー数
- サーバーのIPv4アドレスとそのMAC（Media Access Control）アドレス
- `sudo` プログラムで実行されたコマンド数

> ℹ️ **情報：** ピアレビューの際には、このスクリプトがどのように動作するかを説明するよう求められます。また、スクリプトを変更せずに中断させる必要もあります。`cron` について調べておいてください。

## 第VIII章　提出と相互評価

提出が必要なのは、期待される `README.md` ファイルと、Gitリポジトリのルートに置く `signature.txt` ファイルのみです。このファイルには、仮想マシンのディスクの署名を貼り付ける必要があります。この署名を取得するには、まずVMが保存されているデフォルトのインストールフォルダを開きます。

- Windows: `%HOMEDRIVE%%HOMEPATH%\VirtualBox VMs\`
- Linux: `~/VirtualBox VMs/`
- MacM1: `~/Library/Containers/com.utmapp.UTM/Data/Documents/`
- MacOS: `~/VirtualBox VMs/`

次に、仮想マシンの `.vdi` ファイル（UTMユーザーの場合は `.qcow2`）から、sha1形式で署名を取得します。`rocky_serv.vdi` というファイルを例にした4つのOS別コマンド例を以下に示します。

- Windows: `certUtil -hashfile rocky_serv.vdi sha1`
- Linux: `sha1sum rocky_serv.vdi`
- Mac M1の場合: `shasum rocky.utm/Images/disk-0.qcow2`
- MacOS: `shasum rocky_serv.vdi`

出力結果の例：
- `6e657c4619944be17df3c31faa030c25e43e40af`

> ℹ️ **情報：** 仮想マシンの署名は、再度起動するたびに変化してしまうことに注意してください。全ての評価で署名の検証ができるようにするには、仮想マシンのディスクファイルを複製するか、評価ごとにスナップショットを使用してください。

> ⚠️ **注意：** 仮想マシンをGitリポジトリに含めることは、当然ながら禁止されています。防衛の際には、`signature.txt` ファイルの署名と実際の仮想マシンの署名が比較されます。この2つが一致しない場合、評価点は0点になります。

> ⚠️ **注意：** スナップショットの使用は制限されています。各防衛は、スナップショットが存在しない状態から開始する必要があります。防衛専用のスナップショットは、防衛開始時に作成され、防衛終了時に削除されます。課題を提出する前に、スナップショット機能を使ったテストを行っておくことが推奨されます。

防衛の際、プロジェクトの**ちょっとした変更**を求められることがあります。これは、動作の軽微な変更であったり、数行のコードの記述・書き換えであったり、簡単に追加できる機能であったりします。

この手順は全てのプロジェクトに当てはまるわけではありませんが、評価ガイドラインに記載されている場合に備えて準備しておく必要があります。

この手順は、プロジェクトの特定の部分について実際に理解しているかどうかを確認するためのものです。変更は、自分が選んだ任意の開発環境（例：普段使っている環境）で行うことができ、特に時間制限が定められていない限り、数分で実現可能な程度のものになります。
例えば、関数やスクリプトの小さな更新、表示の修正、新しい情報を保存するためのデータ構造の調整などを求められることがあります。

詳細（範囲、対象など）は**評価ガイドライン**に明記され、同じ課題であっても評価ごとに内容が異なる場合があります。
