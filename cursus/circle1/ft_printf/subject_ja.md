## I. はじめに

C の有名で汎用的な関数 `printf()` を発見することになります。この課題はプログラミングスキルを磨く絶好の機会です。難易度は中程度です。

C における **可変長引数関数（variadic functions）** を学びます。

成功する `ft_printf` のカギは、**構造化されていて拡張しやすいコード**です。

> **情報:** この課題を合格すると、`ft_printf()` を libft に追加して、42 の C プロジェクトで使えるようになります。

## II. 共通ルール

- プロジェクトは **C 言語**で書くこと。
- プロジェクトは **Norm（コーディング規約）** に従って書くこと。ボーナスファイル・関数も Norm チェックの対象になり、Norm エラーがあれば **0 点**になる。
- 関数が予期せず終了してはならない（セグメンテーションフォルト、バスエラー、ダブルフリーなど）。未定義動作を除き、これが発生した場合はプロジェクトが機能していないとみなされ、評価で **0 点**になる。
- ヒープ確保したメモリは、必要に応じて適切に解放すること。**メモリリークは許容されない。**
- 課題が要求する場合、`-Wall`・`-Wextra`・`-Werror` フラグを使い `cc` でソースファイルをコンパイルする `Makefile` を提出すること。`Makefile` は不要な再リンクを行ってはならない。
- `Makefile` には少なくとも `$(NAME)`・`all`・`clean`・`fclean`・`re` のルールを含めること。
- ボーナスを提出する場合、`Makefile` に `bonus` ルールを含めること。このルールは、メインパートで許可されていないヘッダ・ライブラリ・関数をすべて追加する。ボーナスは `_bonus.{c/h}` ファイルに配置すること（課題で別途指定がない限り）。必須パートとボーナスパートの評価は**個別に行われる**。
- プロジェクトで `libft` の使用が許可されている場合、ソースと `Makefile` を `libft` フォルダにコピーすること。プロジェクトの `Makefile` は、まずライブラリをその `Makefile` でビルドし、その後プロジェクトをコンパイルすること。
- テストプログラムの作成を推奨する（提出・採点の対象外）。自分や仲間の作業を簡単にテストできる。ディフェンス中に自分のテストや評価相手のテストを自由に使ってよい。
- 課題を指定の Git リポジトリに提出すること。リポジトリ内の作業のみが評価対象になる。Deepthought が採点を担当する場合、ピア評価後に実施される。Deepthought の採点中にエラーが発生した場合、評価はそこで停止する。

## III. AI に関する指示

このプロジェクトは、ICT トレーニングの基礎的な構成要素を発見する助けとなるよう設計されています。

重要な知識とスキルを確実に定着させるために、AI ツールやサポートの使い方に対して慎重なアプローチを取ることが不可欠です。

真の基礎学習には、困難・反復・ピアラーニング（仲間との学び合い）を通じた**本物の知的努力**が必要です。

AI に対する42のスタンス（学習ツールとして、ICT カリキュラムの一部として、就職市場での期待として）の全体像については、イントラネット上の専用 FAQ を参照してください。

### 主なメッセージ

- 近道をせず**強固な基礎**を築くこと。
- **テクニカルスキルと実践力**を本当に伸ばすこと。
- **本物のピアラーニング**を経験し、学び方と新しい問題の解き方を学ぶこと。
- **学習の過程は結果よりも重要**である。
- AI に関連するリスクを理解し、よくある落とし穴を避けるための効果的な管理手法と対策を身につけること。

### 学習者のルール

- 課題に取り組む際は、AI に頼る前にまず**自分で考える**こと。
- AI に**直接答えを求めてはならない**。
- 42 の AI に対する全体的なアプローチについて**学ぶこと**。

### このフェーズで得られる成果

- 適切なテクニカル・コーディングの基礎を身につける。
- このフェーズで AI がなぜ・どのように危険なのかを理解する。

### コメントと具体例

- AI が存在することは知っている。AI はあなたのプロジェクトを解くことができる。しかしあなたがここにいるのは**学ぶため**であり、AI が学んだことを証明するためではない。AI が問題を解けることを示すだけに時間（あなたの、そして私たちの）を無駄にしないこと。
- 42 での学習は答えを知ることではなく、**答えを見つける能力を養うこと**。AI は答えを直接与えるが、それによって自分自身の論理的思考を育てる機会が失われる。論理的思考は時間・努力・失敗を伴うものだ。成功への道は簡単であるべきではない。
- 試験中は AI が使えない（インターネットも、スマートフォンも、その他も）。学習プロセスで AI に頼りすぎていたとすぐに気づくことになる。

- AI はカリキュラムの一部になる。学習ツールとしても、それ自体がトピックとしても。自分の AI ソフトウェアを構築する機会もある。段階的なアプローチについては、イントラネットのドキュメントを参照のこと。

**良い例:**
> 新しいコンセプトで詰まった。近くにいる人にどうアプローチしたか聞いてみた。10分話したら突然わかった。理解できた。

**悪い例:**

## IV. 必須パート

| 項目 | 内容 |
|------|------|
| **プログラム名** | `libftprintf.a` |
| **提出ファイル** | `Makefile`, `*.h`, `*/*.h`, `*.c`, `*/*.c` |
| **Makefile** | `NAME`, `all`, `clean`, `fclean`, `re` |
| **使用可能な外部関数** | `malloc`, `free`, `write`, `va_start`, `va_arg`, `va_copy`, `va_end` |
| **libft 使用** | 可 |
| **説明** | `printf()` の動作を模倣する `ft_printf()` 関数を含むライブラリを作成する |

`libc` の `printf()` 関数を再実装すること。

`ft_printf()` のプロトタイプ:

```c
int    ft_printf(const char *, ...);
```

### 要件

- オリジナルの `printf()` の**バッファ管理は実装しない**こと。
- 以下の変換を処理すること: `c` `s` `p` `d` `i` `u` `x` `X` `%`
- 関数はオリジナルの `printf()` と比較されて評価される。
- ライブラリの作成には `ar` コマンドを使うこと。`libtool` コマンドの使用は**禁止**。
- `libftprintf.a` はリポジトリのルートに作成すること。
- ヘッダファイルは `ft_printf.h` という名前にし、`ft_printf()` 関数のプロトタイプを含めること。

### 実装する変換一覧

| 変換指定子 | 説明 |
|-----------|------|
| `%c` | 1文字を出力する |
| `%s` | 文字列を出力する（C 言語の一般的な規約による） |
| `%p` | `void *` ポインタ引数を16進数形式で出力する |
| `%d` | 10進数（基数10）を出力する |
| `%i` | 基数10の整数を出力する |
| `%u` | 符号なし10進数（基数10）を出力する |
| `%x` | 16進数（基数16）を**小文字**で出力する |
| `%X` | 16進数（基数16）を**大文字**で出力する |
| `%%` | パーセント記号を出力する |

## VI. ボーナスパート

すべてのボーナスをやる必要はありません。

ボーナスリスト:

- すべての変換において、以下のフラグの任意の組み合わせを処理すること: `-` `0` と最小フィールド幅
- 以下のすべてのフラグを処理すること: `#` `+` ` `（スペースもフラグの1つ）

> **ヒント:** ボーナスパートを完成させる予定なら、最初から追加機能の実装を考慮に入れること。そうすることで、単純なアプローチによる落とし穴を避けられる。

> **警告:** ボーナスパートは必須パートが**完璧**な場合のみ評価される。必須パートが完全に実装されエラーなく動作している必要がある。必須要件をすべて満たしていない場合、ボーナスパートはまったく評価されない。

## VII. 提出とピア評価

いつも通り Git リポジトリに課題を提出すること。ディフェンス中に評価されるのはリポジトリ内の作業のみ。ファイル名が正しいかどうか必ず確認すること。

この課題を合格すると、`ft_printf()` を `libft` に追加して、42 の C プロジェクトで使えるようになります。

評価中に、プロジェクトの**軽微な修正**が求められることがある。これは、動作の小さな変更、数行のコードの追記や書き直し、または簡単に追加できる機能などが対象。

このステップはすべてのプロジェクトに適用されるわけではないが、評価ガイドラインに記載されている場合は対応できるよう準備しておくこと。

このステップはプロジェクトの特定部分についての**実際の理解度**を確認するためのもの。修正は任意の開発環境（普段使いのセットアップなど）で行うことができ、数分以内に対応できるはず（評価の一部として特定の時間制限が設定されている場合を除く）。

たとえば、関数やスクリプトの小さな更新、表示の変更、新しい情報を格納するためのデータ構造の調整などが求められる可能性がある。

詳細（範囲・対象など）は**評価ガイドライン**に記載され、同じプロジェクトでも評価ごとに異なる場合がある。
