# 導入

以下のルールを遵守してください。

- 評価プロセス全体を通して、礼儀正しく、丁寧で、敬意を払い、建設的な態度を保ってください。コミュニティの健全な運営は、こうした態度にかかっています。

- 評価対象の学生またはグループのプロジェクトにおける潜在的な問題点を特定してください。特定された問題について、時間をかけて話し合い、議論してください。- プロジェクトの指示や機能範囲について、同僚によって理解の仕方が異なる場合があることを考慮してください。常に先入観を持たずに、できる限り正直に評価してください。ピア評価を真剣に受け止めてこそ、教育は効果を発揮します。

# ガイドライン

- 評価対象の学生またはグループの Git リポジトリに提出された作品のみを採点してください。

- Git リポジトリが学生のものであり、プロジェクトが想定どおりのものであることを確認してください。さらに、「git clone」が空のフォルダで実行されていることを確認してください。

- 悪意のあるエイリアスが使用されておらず、公式リポジトリの内容ではないものを評価させられていないことを注意深く確認してください。

- 予期せぬ事態を避けるため、また該当する場合は、採点を容易にするために使用されたスクリプト(テスト用または自動化用のスクリプト)を一緒に確認してください。

- 評価する課題を完了していない場合は、評価プロセスを開始する前に、主題全体を読まなければなりません。

- 利用可能なフラグを使用して、空のリポジトリ、機能しないプログラム、ノルムエラー、不正行為などを報告してください。これらの場合、評価プロセスは終了し、最終成績は0、不正行為の場合は -42 となります。ただし、不正行為を除き、学生は提出された作品を一緒に確認し、今後繰り返されるべきではない間違いを特定することを強く推奨します。

メモリリークがないことも確認する必要があります。ヒープに割り当てられたメモリは、実行終了前に適切に解放されなければなりません。leaks、valgrind、e_fence など、コンピュータで利用可能なさまざまなツールを使用してください。メモリリークが検出された場合は、適切なフラグを選択してください。

# 予備

評価を開始する前に、必ず主題全体を読み、理解していることを確認してください。

## グループ

評価は、採点対象となる両方の学習者が立ち会う中で行われます。このように、他者との交流を通して誰もが成長していくのです。

- 弁論の際には、両方の学習者が出席しなければならない。
- 報告なし：0、レビューは終了しました。
- 演習が機能しなくなった時点で、レビューは終了します。以下の演習のコードは閲覧できますが、採点対象にはなりません。

## 検証

グループプロジェクトの検証：

- リポジトリの貢献者として、学習者が正確に2人登録されていることを確認してください。
- 両方の学習者が、実装されたコードのどの部分についても説明し、擁護できることを確認してください。
- README.mdファイルに各学習者の貢献内容が明確に記載されていることを確認してください。
- 両学習者は、自身の担当部分だけでなく、コードベース全体を理解していることを証明しなければなりません。これらの要件のいずれかが満たされない場合、評価は不合格となります。

## README.md 準拠チェック

リポジトリのルートにREADME.mdファイルが存在し、かつ以下の内容がすべて含まれていますか？

- 最初の行は斜体で、次のように正確にフォーマットされています: このアクティビティは、`<login1>`、`<login2>` によって 42 カリキュラムの一部として作成されました(必要な学習者は正確に 2 人です)。
- 活動の目的を説明し、簡単な概要を提供する「説明」セクション。
- コンパイル、インストール、および／または実行に関する詳細情報を記載した「手順」セクション。
- 「リソース」セクションでは、参考文献（ドキュメント、チュートリアルなど）を一覧表示し、AIがどのように使用されたか、どのタスクやプロジェクトのどの部分で使用されたかを具体的に説明します。
- このアクティビティで選択されたアルゴリズム（単純な O(n²)、中程度の O(n√n)、複雑な O(n log n)、および適応戦略）の詳細な説明と正当性。
- 各学習者のプロジェクトへの貢献を明確に記録すること。

```
$> make
```

を実行してコンパイルをテストし、push_swap 実行可能ファイルが作成されることを確認してください。

```
$> make clean
$> make fclean
$> make re
```

が正しく動作することを確認してください。
コンパイルエラーが発生した場合、または Makefile が正しく動作しない場合は、評価はここで終了します。コードの実装について議論を続けることはできますが、この課題は採点されません。

注：実装によっては軽微なメモリの問題は許容される場合がありますが、重大なメモリリークやクラッシュが発生した場合は、エラーとして処理されるべきです。

## ベンチマークモードと障害計算

注：主要な情報が含まれている場合は、出力形式に若干の差異があっても許容されます。
