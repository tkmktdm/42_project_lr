## 第II章 共通ルール

- プロジェクトは C で書くこと。
- プロジェクトは **Norm（コーディング規約）** に従って書くこと。ボーナスファイル・ボーナス関数も Norm チェックの対象となり、Norm エラーがあれば 0 点になります。
- 関数が予期せず終了してはいけません（セグメンテーションフォルト、バスエラー、ダブルフリーなど）。未定義動作の場合を除き、このような事態が発生するとプロジェクトは「動作不良」と見なされ、評価で 0 点になります。
- ヒープに確保したメモリは、必要に応じて適切に解放すること。メモリリークは認められません。
- 課題で求められる場合、`cc` を使って `-Wall`、`-Wextra`、`-Werror` フラグでソースファイルをコンパイルする `Makefile` を提出すること。`Makefile` は不要な再リンクを行ってはいけません。
- `Makefile` には少なくとも `$(NAME)`、`all`、`clean`、`fclean`、`re` のルールを含めること。
- ボーナスを提出する場合、`Makefile` に `bonus` ルールを含めること。このルールは、メインパートで使用が認められていないヘッダ・ライブラリ・関数をすべて追加します。ボーナスは（課題で別途指示がない限り）`_bonus.[c/h]` ファイルに配置すること。必須パートとボーナスパートの評価は別々に行われます。
- `libft` の使用が許可されている場合、そのソースと `Makefile` を `libft` フォルダにコピーすること。プロジェクトの `Makefile` は先に `libft` フォルダの `Makefile` でライブラリをコンパイルし、その後プロジェクトをコンパイルすること。
- テストプログラムを作成することを推奨します（**提出不要・採点対象外**）。自分の実装やピアの実装を簡単にテストするための機会になります。防衛（defense）の際に特に役立ちます。防衛では、自分のテストや評価相手のテストを自由に使えます。
- 課題を指定された Git リポジトリに提出すること。採点されるのは Git リポジトリ内の内容のみです。Deepthought が採点する場合は、ピア評価の後に行われます。Deepthought の採点中にいずれかのセクションでエラーが発生すると、評価はそこで停止します。

## 第IV章 必須パート

| 項目             | 内容                                                                  |
| ---------------- | --------------------------------------------------------------------- |
| **関数名**       | `get_next_line`                                                       |
| **プロトタイプ** | `char *get_next_line(int fd);`                                        |
| **提出ファイル** | `get_next_line.c`、`get_next_line_utils.c`、`get_next_line.h`         |
| **パラメータ**   | `fd`：読み込むファイルディスクリプタ                                  |
| **戻り値**       | 読み込んだ行：正常動作 / `NULL`：読み込むものがない、またはエラー発生 |
| **使用可能関数** | `read`、`malloc`、`free`                                              |
| **説明**         | ファイルディスクリプタから読み込んだ1行を返す関数を書く               |

### 仕様

- `get_next_line()` を繰り返し呼び出す（例：ループ）と、ファイルディスクリプタが指すテキストファイルを **1行ずつ** 読み込めること。
- 読み込んだ行を返すこと。読み込むものがない場合やエラーが発生した場合は `NULL` を返すこと。
- ファイルの読み込み時と標準入力からの読み込み時の両方で正しく動作すること。
- **注意：** 返す行には終端の `\n` 文字を含めること。ただし、ファイルの末尾に達し、ファイルが `\n` で終わっていない場合はこの限りではない。
- ヘッダファイル `get_next_line.h` には少なくとも `get_next_line()` 関数のプロトタイプを含めること。
- 必要なヘルパー関数はすべて `get_next_line_utils.c` ファイルに追加すること。

> **ヒント:** `static` 変数とは何かを理解することが良いスタート地点です。

### BUFFER_SIZE について

- `get_next_line()` でファイルを読み込む際、コンパイル時に `-D BUFFER_SIZE=n` オプションを追加すること。これにより `read()` のバッファサイズが定義されます。バッファサイズの値は、ピア評価者と Moulinette があなたのコードをテストする際に調整されます。

> **警告:** このプロジェクトは通常のフラグに加えて `-D BUFFER_SIZE` フラグあり・なしの両方でコンパイルできなければなりません。任意のデフォルト値を選んでかまいません。

- コンパイル例（バッファサイズ 42 の場合）：

  ```
  cc -Wall -Wextra -Werror -D BUFFER_SIZE=42 <ファイル>.c
  ```

- `get_next_line()` は、最後の呼び出し以降にファイルディスクリプタに関連付けられたファイルが変更された場合（`read()` がまだファイル末尾に達していない状態で）、未定義動作を示します。
- `get_next_line()` はバイナリファイルの読み込み時も未定義動作を示します。ただし、この動作を処理する論理的な方法を実装してもかまいません。

> **考えてみよう:** `BUFFER_SIZE` の値が 9999 の場合でも関数は正しく動きますか？ 1 の場合は？ 10000000 の場合は？ なぜそうなるかわかりますか？

> **ヒント:** `get_next_line()` が呼ばれるたびに、できるだけ少ない読み込みを心がけること。改行に出くわしたら、現在の行を返すこと。ファイル全体を読み込んでから各行を処理するのではありません。

### 禁止事項

- このプロジェクトでは `libft` の使用は禁止。
- `lseek()` は禁止。
- グローバル変数は禁止。

## 第VI章 ボーナスパート

このプロジェクトはシンプルなので、複雑なボーナス機能はありません。しかし、あなたの創造性を信頼しています。必須パートを完成させたら、このボーナスパートに挑戦してみてください。

ボーナスパートの要件：

- `get_next_line()` を **静的変数1つだけ** で実装すること。
- `get_next_line()` が **複数のファイルディスクリプタを同時に管理** できること。例えば、ファイルディスクリプタ 3、4、5 から読み込んでいる場合、各呼び出しで別のファイルディスクリプタから読み込みつつ、それぞれの読み込み状態（または別のファイルディスクリプタの行）を失わないようにすること。つまり、fd 3 → fd 4 → fd 5 → fd 3 → fd 4 … という順で `get_next_line()` を呼び出しても、各ファイルディスクリプタの読み込み状態を保持できること。

ボーナスファイルには `_bonus.[c/h]` サフィックスを付けること。必須パートのファイルに加えて、以下の3ファイルを提出すること：

- `get_next_line_bonus.c`
- `get_next_line_bonus.h`
- `get_next_line_utils_bonus.c`

> **警告:** ボーナスパートが評価されるのは、必須パートが **完璧** な場合のみです。「完璧」とは、必須パートが完全に実装されており、誤動作なく動作することを意味します。必須要件を **すべて** クリアしていない場合、ボーナスパートはまったく評価されません。

## 第VII章 提出とピア評価

通常通り、課題を Git リポジトリに提出すること。防衛（defense）では、リポジトリ内の内容のみが評価されます。ファイル名を正確に確認してください。

> **テストを書く際に覚えておくこと：**
>
> 1. バッファサイズも行のサイズも、さまざまな値になりえます。
> 2. ファイルディスクリプタは通常のファイルだけを指すわけではありません。
>    徹底的にテストし、ピアとクロスチェックしましょう。防衛のために多様なテストセットを準備してください。

合格したら、ためらわずに `get_next_line()` を自分の `libft` に追加しましょう。

評価中、**プロジェクトの軽微な修正** を求められることがあります。動作の小さな変更、数行のコードの記述や書き直し、または簡単な機能の追加などです。

このステップは **すべてのプロジェクトに適用されるわけではありません** が、評価ガイドラインに記載されている場合は準備しておく必要があります。

このステップは、プロジェクトの特定の部分についてあなたが本当に理解しているかを確認するためのものです。修正は自分が普段使っている開発環境で行えます。数分以内で実現可能なはずです（評価の一部として特定の時間枠が定められている場合を除く）。例えば、関数やスクリプトの小さな更新、表示の変更、新しい情報を格納するためのデータ構造の調整などを求められることがあります。

詳細（範囲、対象など）は **評価ガイドライン** に明記されており、同じプロジェクトでも評価ごとに異なる場合があります。
